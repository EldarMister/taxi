# API сервера такси

Базовый путь — `/api`. Интерактивная документация: `/api/docs`, JSON OpenAPI: `/api/docs-json`. Денежные поля `price`, `deposit`, `amount`, `commissionTotal`, `cashIncome` — **целые сомы**, код валюты `KGS`. Оплата поездки только `CASH`; наличная выручка никогда не зачисляется на депозит водителя.

## Запуск

1. Node.js 22, PostgreSQL 16 или новее. Скопировать `.env.example` в `.env`, заменить секреты двумя различными случайными строками не короче 32 символов, указать `DATABASE_URL`.
2. `npm ci`, `npm run db:migrate`, `npm run build`.
3. Для тестовых данных: `NODE_ENV=development`, затем `npm run db:seed`.
4. `npm start`. Для разработки: `npm run dev`; в отдельном терминале `npm run watch` пересобирает изменения, а первый процесс перезапускает сервер. Компилируется TypeScript с метаданными декораторов Nest; запуск исходников через esbuild/tsx для приложения не используется.

Dockerfile собирает приложение и запускает миграции перед сервером. Продакшен-контейнер запускается от пользователя `node`. `DATABASE_URL` и секреты передаются окружением. Для реальной эксплуатации нужен TLS на доверенном reverse proxy. По умолчанию Express **не доверяет** `X-Forwarded-For`: IP-лимиты применяются к соединяющемуся адресу; за proxy настройте доверие только к известным адресам инфраструктуры, не ко всем заголовкам клиента.

## Авторизация

| Метод | Путь | Тело / результат |
|---|---|---|
| POST | `/auth/request-code` | `{phone:"+996700123456"}` → `{sent,retryAfterSeconds}` |
| POST | `/auth/verify-code` | `{phone,code}` → `{accessToken,refreshToken,expiresIn,userId,user}` |
| POST | `/auth/refresh` | `{refreshToken}` → `{accessToken,refreshToken,expiresIn,userId,user}` |
| POST | `/auth/logout` | JWT + `{refreshToken}` → `{ok:true}` |

JWT передаётся `Authorization: Bearer <accessToken>`. Access token связан с конкретной refresh-сессией; при каждом REST-запросе сервер проверяет живую запись сессии и читает роль пользователя из БД. Refresh-токены случайные, в БД хранятся только SHA-256 хеши. При ротации старый токен отзывается; повторное использование отозванного refresh-токена отзывает всю семью сессии. Поэтому мобильное приложение обязано объединять одновременные обновления токенов в один запрос и атомарно сохранять новую пару. Токены нужно хранить в системном Keychain/Keystore.

SMS-код действителен 5 минут. Лимиты хранятся в PostgreSQL: 1 запрос/минуту и 5/час на телефон, 20/час на IP; проверка — 5 попыток на код и дополнительные лимиты телефона/IP. Неудачные попытки фиксируются даже при неверном коде. Новый пользователь всегда получает роль `CLIENT`; роль из запроса не принимается.

При `NODE_ENV=development` и `DEV_AUTH_ENABLED=true` применяется шестизначный `DEV_OTP_CODE` (пример: `123456`), явно возвращаемый как `developmentCode` только в этом режиме. Нужно сначала запросить код. При любом другом `NODE_ENV` тестовый вход и development-провайдеры запрещены при старте.

Тестовые пользователи: клиент `+996700123456`; подтверждённые водители `+996700111111` и `+996700222222`; администратор `+996700999999`. Начальный депозит каждого тестового водителя — 1000 сом. Seed идемпотентен и не меняет существующие поездки/балансы. В production seed с тестовыми привилегированными номерами запрещён.

## Профили и конфигурация

`GET/PATCH /users/me`: через PATCH редактируются только `name`, `notifications`, `language` (`ru` или `ky`). Телефон, роль и `photoUrl` таким запросом не меняются; неизвестные поля отклоняются. Для клиента фотография профиля отключена.

`POST /users/me/avatar` доступен только водителю и принимает `multipart/form-data` с единственным полем-файлом `avatar`. Допустимы JPEG, PNG и WEBP размером до 5 МБ; сервер сверяет MIME с сигнатурой, полностью декодирует изображение с лимитом 20 Мп, удаляет метаданные и сохраняет безопасный JPEG 720×720. Бинарник, MIME и время версии хранятся в PostgreSQL; устаревшие внешние URL аватаров удалены из схемы. Ответ — обновлённый пользователь с относительным cache-busting URL вида `/avatars/:id?v=:timestamp`. Публичный `GET /avatars/:id` возвращает изображение; мобильное приложение добавляет этот путь к базовому URL API. URL с актуальным `v` кэшируется как immutable, без актуальной версии требует повторной проверки.

`GET /tariffs` возвращает `{id,name,description,basePrice,pricePerKm,pricePerMinute,minimumPrice,commissionBps,active}[]`. `GET /config` — номер поддержки, валюту и признак development. `GET /health` проверяет доступность PostgreSQL.

`POST /users/me/push-token {token,platform:"android"|"ios"}` регистрирует до 10 устройств. `DELETE /users/me/push-token {token}` удаляет токен текущего пользователя. Клиенту следует удалить push-токен текущего устройства до выхода: `/auth/logout` сам регистрацию push-токена не удаляет.

## Заказы

`Point = {latitude:number,longitude:number,address:string}`. `geometry` — массив `{latitude,longitude}`. OSRM возвращает GeoJSON `[longitude,latitude]`; сервер нормализует порядок до отправки приложению.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/orders/quote` | `{pickup:Point,dropoff:Point,tariffId}` → расчёт с `id`, маршрутом, ценой, `expiresAt` (5 минут) |
| POST | `/orders` | `{quoteId,comment?,passenger?:{name,phone},idempotencyKey}` → зафиксированный заказ; `passenger` указывается для поездки другому человеку |
| GET | `/orders/active` | Текущий заказ или JSON `null`; восстановление после запуска/переподключения |
| GET | `/orders/:id` | Доступен только текущим участникам; позволяет восстановить итоговый экран |
| GET | `/orders/history?period=today\|week\|all` | Последние 100 заказов; «сегодня» по Бишкеку UTC+6, неделя — сегодня и 6 предыдущих дней |
| POST | `/orders/:id/accept` | Подтверждённый водитель принимает предложенный ему заказ |
| POST | `/orders/:id/skip` | Водитель пропускает предложение |
| POST | `/orders/:id/arrive` | `ASSIGNED → ARRIVED` |
| POST | `/orders/:id/start` | `ARRIVED → IN_PROGRESS` |
| POST | `/orders/:id/complete` | `IN_PROGRESS → COMPLETED`; однократное списание комиссии |
| POST | `/orders/:id/cancel` | Клиент: отмена до начала; водитель: возврат в поиск до начала |
| POST | `/orders/:id/coming` | Уведомление «Я выхожу» в состоянии `ARRIVED`; статус не меняется |
| GET/POST | `/orders/:id/messages` | POST `{text,clientMessageId}`; текстовый чат участников активной поездки |
| POST | `/orders/:id/rating` | `{score:1..5,comment?:string}`; комментарий до 500 символов, однократно после завершения |
| POST | `/orders/:id/client-rating` | Водитель оценивает пассажира после завершения: `{score:1..5,comment?:string}`; комментарий до 500 символов, однократно |

Полный заказ содержит `id,status,pickup,dropoff,geometry,distanceMeters,durationSeconds,price,currency,paymentMethod,comment,passenger,createdAt,updatedAt,searchExpiresAt,completedAt,driver,client,rating,clientRating,driverRating,tariff,routeProvider`. `passenger` — имя и телефон другого пассажира либо `null`; `client` остаётся владельцем заказа и участником чата. В предложении водителю видно имя другого пассажира, но его телефон передаётся только после принятия заказа. `rating` — оценка водителя пассажиром для этой поездки; `clientRating` — средний рейтинг заказчика только по поездкам, где он сам был пассажиром; `driverRating` — оценка пассажира водителем для этой поездки. `driver.driverProfile` включает `carMake,carColor,carPlate,rating,verified,online`. Для нового водителя рейтинг `null`. Текущее положение водителя не хранится в заказе и не входит в ответ. Водитель передаёт текущую точку в `/routes` для построения маршрута до подачи или назначения; постоянного серверного трекинга нет.

Предложения водителю содержат `clientRating`, но не содержат профиль клиента или других водителей. После отмены водителем ответ — безопасное подтверждение освобождения заказа со статусом `SEARCHING`, `driver:null`, без клиента; приложение убирает активный заказ водителя.

При замене водителя сообщения предыдущего назначения не показываются новому водителю. Чтение чата проверяет состав участников под блокировкой заказа, чтобы отмена/переназначение не раскрывали чужую переписку.

Стоимость и комиссия копируются из созданного сервером расчёта. Клиент не может передать свою цену/расстояние; неизвестные поля DTO отклоняются. `idempotencyKey` / `clientMessageId` — строки 8–100 символов. Повтор того же ключа с другим содержимым даёт 409. Повтор завершения не создаёт новую комиссию. Комментарий к оценке обрезается по краям; повтор оценки с тем же баллом и текстом возвращает существующую запись, а изменение любого из них даёт 409.

Поиск выполняется каждые 3 секунды среди подтверждённых свободных водителей на линии, у которых есть автомобиль и достаточный депозит. Геолокация водителей не используется; MVP рассчитан на одну обслуживаемую городскую зону. Истечение `SEARCH_TIMEOUT_SECONDS` переводит заказ в `NO_DRIVER`. При отмене назначенным водителем этот водитель больше не получает данный заказ, другие непропустившие водители получают новое предложение. Пропущенный заказ не навязывается снова.

## Водитель и администратор

`PATCH /driver/online {online}`. Для выхода на линию нужны подтверждение, автомобиль и депозит не меньше `MIN_DRIVER_DEPOSIT`. Для принятия заказа дополнительно нужно покрыть его комиссию. Сойти с линии при активном заказе нельзя; выход из аккаунта не отменяет поездку — при повторном входе она восстанавливается.

`GET /driver/balance → {deposit,cashIncome,commissionTotal,currency,operations}`. Операция `{id,kind:"TOPUP"|"COMMISSION",amount,balanceAfter,note,createdAt}`. Выручка наличными рассчитана отдельно по завершённым поездкам.

`POST /admin/drivers/:id/topup {amount,idempotencyKey,note}` — пополнение с обязательным описанием и записью администратора. `PATCH /admin/drivers/:id/verify {verified,carMake,carColor,carPlate}` — назначение роли водителя и подтверждение автомобиля. Только существующий `ADMIN`, без активного заказа у изменяемого пользователя. Пользователь не может сам себе назначить роль.

## Socket.IO

Подключение к корню сервера, стандартный путь `/socket.io`, `auth: {token: accessToken}`. Самостоятельного входа в комнаты по произвольному `orderId` нет. Сервер проверяет сессию при соединении, каждом входящем событии, отправке события и раз в 10 секунд; отозванные сессии отключаются. После ротации access token нужно переподключить сокет.

Сервер → приложение:

- `session:ready {userId}`, `session:expired`.
- `order:updated <order>`, `order:offer <sanitized order>`.
- `order:withdrawn {orderId}` — предложение недоступно; убрать его/обновить список.
- `chat:message <message>`; дубли объединять по `id`/`clientMessageId`.
- `rider:coming {orderId}`.

Статусы и чат изменяются через авторизованные REST-команды; события затем приходят всем участникам. Сокет не является источником истины: после восстановления сети приложение запрашивает `/orders/active`, `/orders/:id`, `/driver/offers`, `/orders/:id/messages`.

## Провайдеры и эксплуатационные границы

Карты клиента и водителя используют OpenStreetMap. `ROUTING_PROVIDER=osrm` — единственный провайдер маршрутов; расчёт `/orders/quote` получает дорожную дистанцию и длительность от того же OSRM, без приблизительного коэффициента. При ошибке, отсутствии дороги, повреждённой геометрии или таймауте провайдера сервер возвращает 503 и не создаёт фиктивный успешный маршрут/расчёт.

`POST /routes` требует JWT клиента или водителя и принимает `{pickup:Point,dropoff:Point,language?:'ru'|'ky'}`; тариф не нужен. Координаты проверяются по диапазонам, адрес каждой точки — строка 2–250 символов. Лимит — 30 запросов в минуту на пользователя. При указанном языке сервер сверяет имена ближайших участков маршрута с `name:ru`/`name:ky` на дорожных объектах собственного Nominatim. Неподтверждённое имя остаётся пустым: поворот выдаётся без названия улицы. Запросы имён ограничены первыми 12 шагами и бюджетом 2,5 с; данные OSRM и Nominatim зависят от установленных снимков OSM и не обновляются автоматически. Ответ:

```ts
{
  provider: 'osrm',
  distanceMeters: number,
  durationSeconds: number,
  geometry: {latitude:number,longitude:number}[],
  steps: {
    distanceMeters:number,
    durationSeconds:number,
    name:string,
    maneuver:{
      type:string,
      modifier?:string,
      location:{latitude:number,longitude:number},
      bearingBefore:number,
      bearingAfter:number,
      exit?:number
    },
    geometry:{latitude:number,longitude:number}[]
  }[]
}
```

`OSRM_BASE_URL` в development по умолчанию указывает на демонстрационный `https://router.project-osrm.org`. За пределами development нужен явно заданный собственный/выделенный сервис: демонстрационный адрес запрещён при старте. Запрашиваются `driving`, `steps=true`, `geometries=geojson`, `overview=full`; таймаут — 12 секунд. Манёвры `depart`/`arrive`, повороты, направления и номера выездов из кольца передаются приложению для локальной навигации и речи. OSRM на обычном OSM-снимке не учитывает живые пробки.

Адреса: `GET /places/search?q=...` возвращает `{id,address,latitude,longitude}[]`; необязательная пара `latitude,longitude` задаёт центр поисковой области, по умолчанию Бишкек. Поиск ограничен Кыргызстаном, область вокруг центра повышает релевантность, но не исключает остальные города. `GET /places/reverse?latitude=...&longitude=...` возвращает один объект и сохраняет исходную точку пользователя, даже если ближайший OSM-объект находится рядом. Оба маршрута принимают необязательное `language=ru|ky` (по умолчанию `ru`) для выбора языка имени в Photon/Nominatim и требуют JWT; 60 запросов в минуту на пользователя.

`NOMINATIM_BASE_URL` задаёт собственный или совместимый сторонний Nominatim. Без него development-сервер запускается, а адресные API возвращают понятную ошибку 503; в production конфигурация обязательна. Публичный `nominatim.openstreetmap.org` не используется и отклоняется при старте: см. [ограничения публичного Nominatim](https://operations.osmfoundation.org/policies/nominatim/). Никаких тестовых адресов вместо настоящего поиска нет. Поиск выполняется по отправленному пользователем запросу, не при каждом вводимом символе. `NOMINATIM_USER_AGENT` идентифицирует приложение (в production задайте название и настоящий контакт); `NOMINATIM_MIN_INTERVAL_MS` минимум 1000 мс. Search/reverse используют одну последовательную очередь, объединяют одинаковые запросы, кэшируют до 500 результатов на 24 часа (пустые ответы — 5 минут). Ожидание очереди ограничено, запрос провайдера ограничен 10 секундами. Кэш и очередь действуют на один процесс API; при масштабировании перенесите их в общий сервис и соблюдайте лимиты вашего поставщика.

Готовый [запуск собственных OSRM и Nominatim](MAPS.md) использует `docker-compose.maps.yml` в корне и выгрузку Кыргызстана. Подробности мобильной карты и озвучки находятся в `docs/MAPKIT.md`.
SMS: `SMS_PROVIDER=http`, HTTPS `SMS_GATEWAY_URL`, `SMS_GATEWAY_TOKEN`. Адаптер отправляет `{phone,message}` с Bearer авторизацией и считает доставку принятой при HTTP 2xx. Нужно предоставить gateway выбранного SMS-оператора с этим контрактом; конкретный оператор/реальная доставка без реквизитов не проверены.

Push: `PUSH_PROVIDER=expo` с Expo push tokens (`EXPO_ACCESS_TOKEN` нужен только при включённой enhanced push security), либо `firebase` с файлом service account в `GOOGLE_APPLICATION_CREDENTIALS`. Задачи пушей создаются в транзакции изменения заказа и хранятся в PostgreSQL. Воркер повторяет отправку с задержкой до 8 попыток; недействующие device tokens удаляются. В production нужны реальные APNs/FCM/Expo реквизиты и проверки на устройствах. Приём push-провайдером не гарантирует доставку на устройство; Expo delivery receipts пока не опрашиваются, мониторинг исчерпанных попыток следует подключить перед запуском.

Критические операции используют транзакции PostgreSQL с `SELECT ... FOR UPDATE`. Частичные уникальные индексы страхуют один активный заказ клиента/водителя; уникальные записи комиссии и ключей повторов страхуют денежные операции. Депозит не может стать отрицательным. Дополнительные SQL CHECK ограничения находятся в начальной миграции; использовать `migrate deploy`, не `db push`.

Этот MVP рассчитан на один процесс API: Socket.IO события распространяются внутри процесса, Redis adapter/межпроцессная доставка realtime не подключены. PostgreSQL защищает конкуренцию и фоновые push-задачи; перед горизонтальным масштабированием нужен общий event bus/Socket.IO adapter. Поиск пока сканирует до 500 доступных водителей и 200 ищущих заказов за цикл; для большого города нужны PostGIS/геоиндекс и очереди. Чат/история имеют фиксированные пределы 500/100. Аватары водителей пока хранятся в PostgreSQL с лимитом 5 МБ; при росте аудитории их следует вынести в объектное хранилище. Пагинация, антифрод GPS, полноценная админ-панель, мониторинг и восстановление резервных копий — последующие эксплуатационные работы.

## Проверки

`npm test` — расчёт стоимости, расстояния, допустимые переходы, часовой пояс истории, OSRM-геометрия и манёвры, обработка ошибок, очередь/кэш/валидация геокодера. `npm run build` — TypeScript и генерация Prisma.

Интеграции запускаются **только на отдельной одноразовой БД** с `taxi_test` в URL: задать `DATABASE_URL`, `TEST_DATABASE_RESET=true`, применить `npm run db:migrate`, собрать `npm run build`, затем `npm run test:integration`. Тесты очищают таблицы этой БД. Используется настоящий PostgreSQL, полноценное Nest HTTP-приложение и Socket.IO-клиенты: параллельное создание, конкурирующее принятие, один водитель/два заказа, отмены, восстановление, права доступа, координаты, чат, «Я выхожу», комиссии, пополнения, SMS-попытки и отзыв сессий. Они не заменяют проверку Android/iOS на двух физических устройствах и реальных провайдеров.

## Положение водителя активной поездки

- `PATCH /api/orders/:id/driver-location`: авторизованный назначенный DRIVER передаёт `{ latitude, longitude, accuracy, timestamp, heading?, speed? }`; timestamp — время GPS в миллисекундах. Частота приложения — примерно раз в 3 секунды. Сервер проверяет роль, назначение и активный статус под блокировкой заказа, отвергает устаревшие/некорректные точки и не заменяет новую точку старой.
- `GET /api/orders/:id/driver-location`: доступ только участникам заказа. Ответ `{ orderId, driverId, status, location }`. После окончания или 30 секунд без GPS `location: null`.
- Сокет `driver:location` доставляется только клиенту этого заказа. Произвольных публичных комнат и списка координат водителей нет. Клиент проверяет orderId/driverId/status и возраст точки; резервный опрос — раз в 5 секунд.
- Последняя точка хранится в `Order.driverLocation`; после завершения/отмены очищается. История перемещений не накапливается. Нужна миграция `20260915120000_order_driver_location`.
- `SEARCH_TIMEOUT_SECONDS=60` задаёт минуту для принятия нового заказа. Deadline возвращается в `searchExpiresAt` и проверяется сервером.
