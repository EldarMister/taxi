# Atlas — платформа поездок и доставки

Atlas — проект сервиса такси, автомобильной и грузовой доставки, а также заказа еды. Сейчас это **разрабатываемый продукт**, а не готовый к массовому запуску сервис. В репозитории есть работающие пользовательские сценарии, API, административная панель, тесты и Android-сборки. Реальные SMS, push, картографические сервисы, обработка заказов заведениями, юридические страницы и испытания на физических устройствах требуют отдельной настройки и проверки перед релизом. Дата выхода не определена.

Из одного мобильного кода собираются два приложения:

| Приложение | Для кого | Идентификатор Android | Основная задача |
| --- | --- | --- | --- |
| **Atlas** | Клиент, пассажир | `kg.taxigo.app` | Выбрать услугу, оформить заказ и следить за ним |
| **Atlas pro** | Водитель | `kg.taxigo.driver` | Пройти проверку, принимать и выполнять заказы |

Приложения можно установить рядом. Они используют один сервер, но при входе проверяют роль аккаунта и не открывают интерфейс чужой роли. Оператор работает в отдельной веб-панели. Подробности вариантов сборки — в [docs/APP-VARIANTS.md](docs/APP-VARIANTS.md).

## Как устроен продукт

```text
Atlas / Atlas pro ── REST API ──┐
        │                       │
        └──── Socket.IO ────────┤  NestJS ── Prisma ── PostgreSQL
                                │     │
Панель оператора ───────────────┘     ├── OSRM: автомобильные маршруты
                                      ├── Photon / Nominatim: поиск и адреса
                                      └── SMS / push: настраиваемые провайдеры

Мобильная карта: MapLibre + данные OpenStreetMap
```

Мобильный интерфейс отвечает за выбор, отображение и взаимодействие. **Сервер — источник истины** для цены, доступности водителя, назначения, статусов, сообщений и денежных операций. Socket.IO ускоряет обновление экранов; после потери связи приложения запрашивают актуальное состояние у API. Данные заказов и история хранятся в PostgreSQL.

Поездки и автомобильная доставка оплачиваются наличными в кыргызских сомах. Депозит водителя служит для комиссии сервиса; наличная выручка учитывается отдельно. Для еды доступны наличные, а онлайн-эквайринг пока не подключён.

## Пользовательский опыт

### Первый запуск и общий главный экран

Клиент входит по номеру телефона и SMS-коду, проходит запросы разрешений на геолокацию и уведомления. Токены сессии сохраняются защищённо, а при следующем запуске приложение восстанавливает аккаунт и незавершённый заказ.

Главный экран Atlas показывает адрес пользователя, четыре услуги — **Такси**, **Доставка**, **Грузовой** и **Еда** — и кнопку быстрого поиска направления «Куда едем?». Адрес можно изменить через поиск или карту. Есть сохранённые места «Дом», «Работа», «Избранное», уведомления с индикатором непрочитанного и промоблок, содержимое которого меняет оператор. Экран рассчитан на использование одной рукой; в сценарии поездки детали заказа открываются в нижних панелях, оставляя карту на виду.

Интерфейс поддерживает русский и кыргызский языки, светлую и тёмную темы. Экраны и иллюстрации разрабатываются по материалам в `designe/`; сами референсы не являются инструкциями или источником серверной логики.

### Поездка на такси

1. Клиент выбирает точку подачи и пункт назначения: по GPS, через адресный поиск или перемещая карту под центральной меткой. Начальную точку можно уточнить вручную.
2. Сервер получает автомобильный маршрут, дорожное расстояние и примерное время через OSRM. По доступным тарифам он возвращает котировки; изменение адреса пересчитывает их. Просроченную котировку нельзя использовать для создания заказа.
3. Клиент выбирает тариф, при необходимости указывает подъезд, комментарий или другого пассажира и подтверждает наличную оплату. Цена сохраняется при оформлении.
4. Заказ ищет подходящего водителя. Клиент видит статус поиска, затем только назначенного ему водителя, его положение и маршрут подъезда. Можно позвонить, открыть чат, отправить текст или фотографию и сообщить «Я выхожу».
5. После прибытия и начала поездки экран показывает текущий этап и маршрут. По завершении клиент оценивает водителя; поездка доступна в истории. Отмена до начала оформляется через подтверждение.

Карта основана на MapLibre и данных OpenStreetMap. На близком масштабе отображаются доступные в данных светофоры и разметка пешеходных переходов. Наличие объекта зависит от актуальности и полноты OSM. Карта не заменяет наблюдение за дорогой.

### Автомобильная доставка и грузовой заказ

На главном экране это две отдельные кнопки. Обе открывают сценарий доставки с заранее выбранным видом заказа:

- **Доставка** — небольшой груз на легковом автомобиле.
- **Грузовой** — крупный груз для водителя с соответствующим классом машины.

Клиент задаёт адрес отправления и назначения, описание и комментарий. Для грузового заказа доступны дополнительные параметры, например тип кузова, грузчики и запланированная подача. Цена и подходящий класс транспорта определяются сервером. Дальше используются общие этапы поиска, назначения, выполнения, чата, истории и оценки. Водитель получает только заказы тех видов, которые разрешены его профилю и включены им.

### Еда

Клиент открывает каталог ресторанов, ищет и фильтрует блюда, просматривает карточку блюда и дополнения, добавляет позиции в корзину. Корзина и избранное сохраняются для аккаунта; блюда разных ресторанов нельзя незаметно смешать в одном заказе.

При оформлении выбирается доставка по адресу или самовывоз, добавляется комментарий и показывается итоговая сумма. Сервер пересчитывает её перед созданием заказа и защищает повторный запрос от дубля. Активный заказ восстанавливается после перезапуска; изменения статуса приходят по Socket.IO и резервным запросам. История хранит состав и цену на момент оформления.

Сейчас сменой этапов заказа еды управляет оператор: **размещён → подтверждён → готовится → готов → доставляется/выдаётся → завершён**; возможна отмена. Автоматическое назначение курьера и передача заказа реальному ресторану не являются завершённым производственным процессом. Часть каталога — демонстрационные данные. Детали — в [docs/FOOD-API.md](docs/FOOD-API.md).

### Работа водителя в Atlas pro

1. Водитель входит в отдельное приложение и заполняет заявку: личные данные, транспорт, фотографии и необходимые документы. Оператор рассматривает направления работы и документы. Самостоятельно назначить себе класс автомобиля нельзя.
2. После подтверждения водитель выбирает разрешённые виды заказов и выходит **на линию**. Для этого нужны геолокация, подходящий подтверждённый автомобиль и достаточный депозит.
3. Сервер предлагает заказ одному подходящему водителю со свежей GPS-точкой. В предложении видны подача, назначение, сумма, дорожное расстояние, время и комментарий. Водитель принимает или пропускает его; предложение ограничено по времени.
4. После принятия запускается ведение сначала к точке подачи, затем к назначению. Этапы заказа: **Приехал → Начать → Завершить**. Доступны звонок и чат. В заголовке чата водителя используется «Пассажир».
5. После успешного завершения комиссия списывается из депозита один раз, поездка появляется в истории. Оценка пассажира и дальнейшие действия завершения показываются отдельным экраном.

Водитель может включить фоновую передачу координат во время активного заказа, если устройство дало нужное разрешение. Новые предложения и сообщения используют звуки и push при настроенном провайдере. Качество GPS, работу системы энергосбережения и слышимость голосовых подсказок нужно проверять на реальных телефонах.

### Панель оператора

Администратор входит отдельно от мобильных пользователей. Панель позволяет рассматривать заявки и документы водителей, назначать классы автомобилей, управлять депозитом и тарифами, видеть заказы и их историю, вести заказы еды, редактировать рестораны, меню, фотографии и промоблоки. Изменения и решения записываются в журнал. Панель находится в `admin/` и обслуживается сервером; подробности — в [docs/ADMIN.md](docs/ADMIN.md).

## Правила заказов и обновлений

Основной жизненный цикл поездки или автомобильной доставки:

```text
SEARCHING → ASSIGNED → ARRIVED → IN_PROGRESS → COMPLETED
     │          │          │
     └──────────┴──────────┴──────→ CANCELLED
     └─────────────────────────────→ NO_DRIVER
```

Назначение, принятие, отмена и списание комиссии выполняются на сервере с проверкой прав и защитой от повторов. Один водитель не ведёт одновременно несколько активных заказов. Пропущенное предложение переходит следующему подходящему водителю. Если водитель отменил принятый заказ до начала поездки, сервер может вернуть его в поиск. История статусов помогает восстановить экран после обрыва связи.

Маршрут не рисуется прямой линией, если дорожный сервис не ответил. Положение водителя показывается только участникам его заказа; устаревшая точка скрывается. Экранное движение машины сглаживается вдоль подтверждённого дорожного участка, но не выдаётся за точный GPS-замер. Подробности карты и навигации — в [docs/MAPKIT.md](docs/MAPKIT.md) и [docs/DRIVER-TRACKING.md](docs/DRIVER-TRACKING.md).

| Карта и местоположение | MapLibre React Native, OpenStreetMap, Expo Location | Карта, выбор адреса, показ транспорта, GPS |

| Сервер | Node.js, NestJS, TypeScript, Swagger | REST API, роли, бизнес-правила, события и административные операции |
| Данные | PostgreSQL 17, Prisma 6, миграции | Пользователи, тарифы, заказы, сообщения, каталог и аудит |
| Административный интерфейс | Статический веб-интерфейс в `admin/` | Работа оператора через API |
| Публичный сайт | React, Vite, Tailwind CSS | Лендинг, страницы для водителей и юридические страницы |

## Как мы разрабатываем изменения

1. Описываем сценарий для конкретной роли: что видит человек, какое действие совершает и как выглядит результат при плохой сети или отказе. Сверяем UI с материалами в `designe/`, но поведение проверяем по текущему коду и API.
2. Если меняются данные или правила заказа, сначала обновляем серверный контракт, Prisma-схему и миграцию. Цена, права, статус и доступность водителя проверяются на сервере, а не только кнопками в приложении.
3. Обновляем общий мобильный код с учётом двух сборок. Изменение клиентского экрана не должно случайно открывать его водителю и наоборот. Для асинхронных операций учитываем смену аккаунта, повторное нажатие и поздний ответ сети.
4. Запускаем адресные тесты сценария, TypeScript, затем необходимые серверные и мобильные наборы. Интеграционные тесты выполняем только на отдельной БД.
5. Собираем нужный вариант Android и проверяем пакет, номер версии и подпись. Для поведения GPS, камеры, клавиатуры, уведомлений и звука дополнительно нужен реальный телефон; запись о такой проверке помещаем в `docs/VERIFICATION.md`.

## Локальная разработка

Нужны Node.js не ниже 22.13, npm и PostgreSQL 17. Для Android также нужны Android SDK и настроенная среда сборки. Нативная MapLibre-карта требует development build: обычный Expo Go её не содержит.

### 1. База и API

Из корня репозитория:

```powershell
Copy-Item .env.example .env
Copy-Item server/.env.example server/.env
npm --prefix server ci
docker compose up -d db
npm --prefix server run db:migrate
npm --prefix server run db:seed
npm --prefix server run dev
```

В корневом `.env` задайте пароль PostgreSQL. В `server/.env` укажите соответствующий `DATABASE_URL` и два разных случайных секрета не короче 32 символов: `JWT_SECRET` и `OTP_SECRET`. Файлы окружения и ключи не добавляйте в Git. Команда `db:seed` предназначена для **локальной тестовой базы**: она создаёт демонстрационные данные, её нельзя запускать на рабочей базе. Если Docker недоступен, `npm run db:local` запускает локальный PostgreSQL, а `npm run setup:local` подготавливает окружение. Отдельная инструкция для собственных картографических сервисов находится в [server/MAPS.md](server/MAPS.md).

API запускается на `http://localhost:3000/api`, Swagger — на `http://localhost:3000/api/docs`. Контракт запросов и событий — [server/API.md](server/API.md).

В development-режиме возможен тестовый SMS-код при включённом `DEV_AUTH_ENABLED`. Реальную доставку SMS и push он не подтверждает. Для регистрации администратора используется отдельная команда и учётная запись — см. [docs/ADMIN.md](docs/ADMIN.md).

### 2. Мобильные приложения

```powershell
Copy-Item mobile/.env.example mobile/.env
npm --prefix mobile ci
cd mobile
npm run start:client
```

В другом терминале из `mobile/` запустите `npm run android:client`. Для водителя используйте пару `npm run start:driver` и `npm run android:driver`. Metro и нативную команду одного запуска нужно запускать для **одного варианта**. На macOS доступны соответствующие команды `ios:client` и `ios:driver`.

В `mobile/.env` задайте `EXPO_PUBLIC_API_URL`. Для Android Emulator локальный API доступен как `http://10.0.2.2:3000/api`, для физического телефона нужен LAN-адрес компьютера и общая сеть. В production требуется HTTPS. Адрес API встраивается в приложение при сборке: изменение `.env` не перенастраивает уже установленный APK. Параметры MapLibre, TTS, Firebase и вариантов перечислены в [mobile/.env.example](mobile/.env.example) и [docs/APP-VARIANTS.md](docs/APP-VARIANTS.md).

### 3. Необязательный сайт

```powershell
npm --prefix web ci
npm --prefix web run dev
```

Сайт разрабатывается отдельно от приложений. Его сборка и условия публикации описаны в [web/README.md](web/README.md). Черновые юридические страницы требуют заполнения и проверки перед публичным использованием.

## Проверки и сборки

Основные проверки можно запустить из корня:

```powershell
npm --prefix server run build
npm --prefix server test
npm --prefix mobile run typecheck
npm --prefix mobile run test:native
npm --prefix mobile run test:booking
npm --prefix mobile run test:food
npm --prefix mobile run test:navigation
npm --prefix mobile run test:registration
npm --prefix web run build
```

Интеграционные тесты сервера используют **отдельную тестовую базу** и могут очищать её. Порядок запуска — в [server/VERIFICATION.md](server/VERIFICATION.md). Наличие теста или успешной сборки не означает, что SMS, фоновые разрешения, push, речь и вся поездка проверены на конкретном телефоне. Фактические результаты — в [docs/VERIFICATION.md](docs/VERIFICATION.md).

Android-сборки клиента и водителя разделены по `APP_VARIANT`, пакету, Firebase и EAS-профилю. Команды EAS, сведения о подписи и ограничениях локальной сборки — в [docs/APP-VARIANTS.md](docs/APP-VARIANTS.md). APK для прямой установки лежат в `mobile/builds/`, когда они были собраны в конкретном рабочем окружении; чистый checkout не обязан содержать эти бинарные файлы.

## Что остаётся до публичного релиза

- Подключить и проверить production SMS и push для обоих приложений, настроить ключи и доставку уведомлений на устройствах.
- Обеспечить картографические сервисы и адресный поиск, рассчитанные на реальную нагрузку; обновлять данные дорог и объектов.
- Пройти полный сценарий на двух физических телефонах: заказ, назначение, GPS в городе, плохая сеть, фон, звук, восстановление, отмена и завершение. Отдельно проверить iOS-сборки на macOS.
- Организовать работу с реальными ресторанами и курьерами, проверить тарифы, поддержку, возвраты и финансовые правила. Онлайн-оплата пока не подключена.
- Завершить юридические страницы, политику обработки данных, контакты оператора, резервное копирование, мониторинг и процедуры поддержки.

Эти пункты — направления дальнейшей разработки, **не обещание даты выпуска**. Демонстрационный сервер, тестовые рестораны, локальные APK и устаревшие записи в `docs/` следует отличать от проверенного производственного сервиса.
