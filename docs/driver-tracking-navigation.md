# Навигация водителя и движение автомобиля у клиента

Проверка и исправления: 2 октября 2026 года. Документ описывает код в рабочем дереве, автоматические сценарии и оставшиеся проверки на телефонах. Он не подтверждает публикацию новых сборок или развёртывание сервера.

## Стек и цепочка данных

Версии прочитаны из установленных `node_modules/*/package.json`, а не взяты из диапазонов зависимостей:

| Участок | Установленная версия |
| --- | --- |
| React / React Native | 19.1.0 / 0.81.5 |
| Expo | 54.0.37 |
| expo-location / expo-task-manager | 19.0.8 / 14.0.9 |
| @maplibre/maplibre-react-native | 10.4.2 |
| socket.io-client / socket.io | 4.8.3 / 4.8.3 |
| @nestjs/core / @nestjs/websockets | 11.2.3 / 11.2.3 |
| @prisma/client | 6.19.0 |

Карта — MapLibre Native через React Native SDK, геометрия маршрутов и манёвры — OSRM через серверные `/routes`. Отдельная версия запущенного OSRM и разрешённые Gradle/CocoaPods версии нативного движка в этой проверке не устанавливались.

1. `useDriverNavigation` получает локальные координаты через `Location.watchPositionAsync`. Во время активной поездки запрашивается интервал 1000 мс, `BestForNavigation`, `distanceInterval: 0`. Параллельная фоновая задача Expo покрывает свёрнутое приложение и выключенный экран. Запрошенный интервал не считается гарантией ОС.
2. Оба источника поступают в `ingestDriverLocation` и один `DriverGpsFilter`. Здесь проверяются время, порядок измерений, координаты, точность, выбросы, остановка и источник курса.
3. Принятый результат сразу отправляется локальным подписчикам. Навигация водителя и её голосовые подсказки не ждут HTTP или события сервера.
4. `reportDriverPosition` отправляет `PATCH /orders/:id/driver-location`. Минимальный интервал в движении — 900 мс, на остановке — 2500 мс. При занятом соединении сохраняется только последний ожидающий замер, без очереди старых позиций.
5. NestJS проверяет водителя, заказ и назначение. В транзакции фиксируются принятые данные и порядковая версия. Клиент получает `driver:location`; совместимый канал заказа — `driver:location:update`. Для восстановления предусмотрен защищённый `GET /orders/:id/driver-location`.
6. `useClientDriverTracking` объединяет события и опрос каждые 5 секунд, отбрасывает чужие/устаревшие данные, дубликаты и пакеты завершённых сессий. Возраст точки считается от серверного времени при получении с дальнейшим монотонным отсчётом на клиенте.
7. `TrackingPlayback` воспроизводит измерения, `DriverTrackingMarker` обновляет одну GeoJSON-точку через `ShapeSource.setNativeProps`. Отрисовка ограничена 30 кадрами/с и не вызывает перерисовку всего экрана на каждом кадре. Камера читает тот же отображаемый кадр через ref.

## Найденные причины

- `driverTracking` привязывал координаты к запланированной дороге и подставлял её касательное направление вместо фактического курса. На соседней дороге, съезде, развороте и пересечении геометрия плана могла противоречить движению. Плановые повороты отправлялись клиенту как `matchedPath`.
- `TaxiMap` повторно выбирал направление между касательной маршрута, соседними точками и GPS, а затем отдельно анимировал положение. Источники маркера и камеры могли расходиться.
- Старое движение запускалось на каждый пакет на 700–1100 мс. При интервалах 3–5 секунд автомобиль успевал доехать до точки и долго стоял до следующего события. Частоты сети и визуального движения были фактически связаны.
- У водителя анимация маркера была отключена: стрелка сразу переходила на новую GPS-точку, пока камера двигалась собственной анимацией.
- Курс сглаживался несколькими слоями. Фиксированные коэффициенты `.45/.2` дополнительно задерживали поворот. `useDriverNavigation` повторно требовал `speed >= 1.5` и терял корректный курс, когда скорость отсутствовала.
- В некоторых ветвях отсутствие направления превращалось в `0`, то есть в настоящий север. Низкая скорость вместе с шумными координатами не давала надёжного положения носа автомобиля.
- Фильтр остановки пропускал начальные свежие измерения вместо немедленного обновления времени при удержании координаты.
- Проверка новых пакетов и восстановление через сохранённые данные не должны откатывать водителя после переподключения; неизвестную точность нельзя превращать в точность `0`.
- Сервер сохранял точку и её порядковую версию только раз в 10 секунд, а live-кэш менялся до завершения транзакции. Это допускало откат после перезапуска и чтение незакоммиченного положения при сбое БД. Теперь каждая принятая точка сохраняется атомарно до публикации; нагрузка — примерно одна запись БД в секунду на движущегося водителя.
- Повторные проверки скачков в локальном фильтре, сервере и клиенте могли снова отвергнуть уже подтверждённое восстановление GPS. Локальный renderer доверяет единому GPS-фильтру; сервер и клиент подтверждают новую область двумя качественными согласованными измерениями. Дубликат подтверждением не считается.

Перестановка широты/долготы, необходимость поправки `180°` или повторное вычитание поворота карты не подтверждены. Эти поправки не вводились.

## Координаты, курс и изображения

| Значение | Соглашение |
| --- | --- |
| GPS и API | `{ latitude, longitude }`, градусы |
| GeoJSON и `Camera.centerCoordinate` | `[longitude, latitude]`, градусы |
| `speed`, `speedMps` | метры в секунду |
| `accuracy`, `accuracyM` | метры, неизвестное значение — `null` в протоколе |
| `measuredAtMs`, `timestamp` | время измерения, миллисекунды Unix |
| `courseDeg` / локальное историческое имя `heading` | географический курс движения: север 0°, восток 90°, юг 180°, запад 270° |
| `courseAccuracyDeg` | точность курса в градусах, `null`, если источник её не предоставляет |
| `courseSource` | `gps`, `displacement` или `null` при отсутствии нового достоверного курса |
| Направление маркера | географический курс; отсутствие курса остаётся неизвестным |
| Направление камеры | независимое состояние сопровождения; режим курса или север сверху |

Expo `coords.heading` — курс перемещения, а не направление телефона по компасу. В приложении нет режима ориентации карты по телефону и нет подписки `watchHeadingAsync`. Магнитный север не смешивается с географическим. Поворот телефона и смена ориентации экрана не являются источниками курса автомобиля. Проверка такого поведения на физических датчиках ещё требуется.

При уверенном движении используется GPS-курс. Порог начала — 2 м/с, продолжения — 1.1 м/с; остановка определяется при скорости до 0.7 м/с с подтверждением. При отсутствии надёжного курса фильтр накапливает качественные измерения: смещение должно превышать 8 м и 1.5 совместной погрешности двух точек. Устаревшая база расчёта не используется. На остановке сохраняется последнее достоверное направление; если его ещё нет, отображается нейтральная точка.

`courseSource: null` с ненулевым/нулевым числовым `courseDeg` означает удерживаемый известный курс без нового подтверждения. `courseDeg: null` означает неизвестное направление. Ноль градусов не является отсутствующим значением. Поля `courseAccuracyDeg` и `courseSource` необязательны для ранее выпущенных клиентов; обновлённый отправитель задаёт их явно.

Существующие `tracking-car-white.png` и `driver-navigation-arrow.png` имеют прозрачный фон и направлены носом/остриём вверх. Константы `VEHICLE_ASSET_BEARING_OFFSET_DEG` и `ARROW_ASSET_BEARING_OFFSET_DEG` документируют offset **0°**. Центр и географическая привязка — `iconAnchor: 'center'`, `iconOffset: [0, 0]`.

В `SymbolLayer` установлены `iconRotationAlignment: 'map'` и `iconPitchAlignment: 'map'`. Угол `iconRotate` задаётся по часовой стрелке в градусах; SDK сам учитывает поворот и наклон карты. Дополнительного вычитания camera bearing нет. Это соответствует [MapLibre Style Spec: icon-rotation-alignment](https://maplibre.org/maplibre-style-spec/layers/#icon-rotation-alignment) и [icon-rotate](https://maplibre.org/maplibre-style-spec/layers/#icon-rotate). API `ShapeSourceRef.setNativeProps` проверен по установленному `mobile/node_modules/@maplibre/maplibre-react-native/src/components/ShapeSource.tsx`: GeoJSON автоматически сериализуется в JSON перед передачей нативному источнику.

## Плавность, камера и маршрут

Локальный фильтр подавляет выбросы и мелкое дрожание, а коэффициент положения зависит от точности, скорости и реального времени между измерениями. Проверенный GPS-курс не сглаживается второй раз до визуального слоя. Одиночный большой скачок требует подтверждения; длинный разрыв разрешает повторное получение позиции.

У водителя нет сетевого буфера. Перенаправление визуальной анимации начинается от текущего отображаемого положения. Краткое локальное предсказание допускается только при качественной точке, скорости и текущем подтверждённом курсе, ограничено 750 мс и 15 м. Удерживаемый курс без нового подтверждения не даёт права предсказывать. При длительном отсутствии измерений маркер возвращается к последней фактической точке.

У клиента применяется интерполяция времени измерения с адаптивным буфером одного интервала поступления плюс запас на неравномерность; буфер ограничен 650–6000 мс. При редких пакетах 5 секунд задержка будет заметно больше, чем при штатном секундном потоке. Клиент не продолжает бесконечное движение за последнюю известную точку. Повороты интерполируются по кратчайшей дуге, включая 359° → 1°. После 5 секунд интерфейс сообщает о задержке; после 15 секунд — об отсутствии актуального положения, сохраняя последнюю точку.

Режимы камеры: «По направлению движения» и «Север сверху». Положение, угол, наклон и масштаб обновляются одним прерываемым потоком, без очереди длительных нативных анимаций. В навигации обзор смещён на 30–80 м вперёд по фактическому курсу. Это только визуальное смещение камеры: оно не меняет GPS, отправляемые координаты или расстояние до манёвра. Ручной жест приостанавливает сопровождение; кнопка возврата восстанавливает его. Существующее автоматическое возобновление водителя после 12 секунд работает только при свежем GPS.

`routeProgress` и `guidanceCue` остаются общими для переднего плана и фоновой навигации. Они используют отфильтрованные локальные измерения и манёвры OSRM. Привязка к плану допустима для вычисления прогресса/обрезки линии подсказки; она больше не управляет положением или курсом машины. Вне маршрута и при старом GPS голосовые указания о поворотах блокируются. Сохраняется существующая разница условий перестроения: в фоне — пять отклонений и ограничение частоты запроса; в переднем плане дополнительно проверяются длительность отклонения и пройденное расстояние.

Последовательность реально полученных точек сохраняет измеренные углы. Запланированная геометрия и старое `matchedPath` не выдаются за реально пройденную дорогу. Если между двумя редкими измерениями нет фактических данных поворота, точно восстановить траекторию через перекрёсток нельзя: прямая интерполяция может срезать угол. Уверенного нового map matching фактически пройденного участка эта правка не добавляет. `POST /routes/match` при перестроении служит выбору начала нового маршрута, а не перемещению маркера.

GPS определяет направление перемещения. При заднем ходе оно может отличаться от ориентации кузова. Приложение не заявляет определение физического носа автомобиля без дополнительного источника.

## Воспроизводимые проверки

Из корня репозитория, после установки зависимостей:

```powershell
npm --prefix mobile run typecheck
npm --prefix mobile run test:tracking
npm --prefix mobile run test:navigation
npm --prefix mobile run test:native
npm --prefix server test
npm --prefix server run build
```

Автоматические проверки используют фиксированные измерения и управляемое время. Покрываются стороны света, левый/правый поворот, разворот, переход через север, удержание на остановке, медленный старт без скорости от ОС, шум и выбросы GPS, съезд с запланированной дороги, интервалы 1/3/5 секунд, задержки, дубликаты, обратный порядок, смена сессии/заказа, потеря связи и восстановление. Проверки компонентов используют подмену нативных API. Они не подтверждают визуальное качество GPU-рендеринга или работу датчиков реального телефона.

## Проверка физических устройств

На первом этапе `adb devices -l` вернул пустой список. Позже пользователь подключил Android-телефон и разрешил USB-отладку для установки новых APK. Дорожная проверка и проверка iOS ещё не выполнены. Перед выпуском нужен следующий прогон на обеих поддерживаемых мобильных платформах, отдельно в водительской и клиентской сборках:

| Сценарий | Что проверить |
| --- | --- |
| Север, восток, юг, запад | Машина и стрелка указывают географический курс; «Север сверху» не меняет курс маркера |
| Правый/левый поворот, разворот, 359° → 1° | Кратчайший плавный поворот маркера и камеры, без полного оборота и удержания старой дороги |
| Остановка, дрожание, медленный старт | Положение не блуждает от мелких ошибок, курс удерживается; на старте обновляется после достоверного движения |
| Поворот телефона, портрет/альбом | Географический курс автомобиля не зависит от телефона; камера и привязка иконки сохраняются |
| Ручной поворот и масштаб клиента | Маркер сохраняет географическое направление и координату при любом bearing/zoom карты |
| Перемещение карты водителя и возврат | Сопровождение приостановлено; возврат плавный, без борьбы независимых анимаций |
| Пакеты 1/3/5 секунд, jitter, duplicate/reorder | Непрерывная интерполяция между событиями, отсутствие отката по старому пакету |
| Отключение сети на 20–60 секунд | Предсказание прекращается; виден статус возраста и последняя фактическая позиция |
| Восстановление GPS/сети и новый заказ | Актуальная позиция принимается, завершённая сессия не оживает, старая очередь не воспроизводится |
| GPS-выброс и соседняя параллельная дорога | Одиночный выброс не телепортирует машину; подтверждённое новое положение принимается без принуждения к плану |
| Фон, блокировка, возврат и повторное открытие карты | Нет дублирующихся подписок/RAF, координаты и голос продолжаются в предусмотренном режиме, ресурсы очищаются |
| Длительная поездка, наклон камеры и слабое устройство | Размер и центр иконки стабильны, нет заметных рывков, утечек или перегрузки обновлениями источника |

## Дорожная запись в Atlas pro 1.1.64

Оранжевая отладочная точка и полигон точности больше не рисуются поверх местоположения водителя. При известном достоверном курсе используется прежний ассет синей стрелки с прежним масштабом и географическим вращением. До появления достоверного направления показывается синяя отметка с белой обводкой и мягким ореолом; неизвестный курс не подменяется севером.

Кнопка «Запись поездки» вынесена из подсказки навигации в отдельное окно на карте водителя. Она доступна до заказа, во время него и после завершения. Открытие диагностики не меняет высоту подсказки или область сопровождения камеры. Закрытие окна не останавливает запись; записанные данные сохраняются при уходе с карты и перезапуске приложения. Новые точки в фоне зависят от работающего GPS-сервиса и разрешений Android.

Порядок дорожной проверки:

1. Установить Atlas pro 1.1.64. В прежней 1.1.63 сохранения файла нет.
2. На карте открыть «Запись поездки» → «Начать запись», проверить увеличение количества точек и вернуться на карту.
3. Во время поездки оставить живой GPS. Для дорожной записи не включать заморозку и синтетический повтор.
4. После поездки открыть «Запись поездки» → «Остановить запись» → «Сохранить файл», выбрать папку на телефоне.
5. Передать файл `atlas-gps-….jsonl` вместе с кратким описанием проблемы и временем, когда она появилась.

Журнал содержит заголовок с версией приложения, исходные и обработанные GPS-точки, причины отбрасывания, контекст сессии/заказа, события отправки координат (включая ошибки связи) и состояние навигации раз в секунду. Он не записывает токены входа, сообщения, контакты или учётные данные. Каждое событие дописывается в файл; память для локального повтора остаётся ограничена 1000 точками, а файл имеет отдельный предел 32 МБ. При ошибке хранения запись останавливается с сообщением, уже записанные точки сохраняются, а живой GPS продолжает работать. Отмена выбора папки не удаляет исходный журнал. Неполная последняя строка после аварийного завершения не мешает восстановлению и не попадает в экспорт.
