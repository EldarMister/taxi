## Что подтверждено для прежнего прогона 500

Прогон `500-20261012T202801494Z` выполнялся на Windows, API, PostgreSQL 18.4 и генераторы делили физический Ryzen 5 6600H / 12 логических CPU / 23 869 MiB. API pool=10, max_connections=60, маршруты были детерминированной локальной заглушкой. Это не испытание фактического Railway-релиза или реальных карт.

`1212` — **код ошибки k6**, не количество отказов. Полные исходные потоки содержат 1231 отказ HTTP-реестра акторов и 278 отказов чтения API: все с кодом 1212 и строкой `dial: connection refused`. Всего 1509. Реестр получил 1711 обращений вместо необходимых 480. Все его отказы завершились между 20:28:06.067 и .322 UTC; отказы API — между .364 и .415 UTC. Отказ получения слота выбрасывал исключение до обычного sleep, поэтому VU немедленно начинал следующую итерацию и повторял регистрацию. Реестр открывался до запуска генераторов и закрывался после их окончания; преждевременное закрытие не следует из кода.

Независимо от этих отказов, в окне 60–70 секунд от начала прогона наблюдался второй всплеск: p95 успешных чтений 1283 мс, p95 обработки 2019 мс, без отказов TCP. Это окно совпадает с запланированным переподключением Socket.IO. Снимок API в 20:29:10.879 UTC показал RSS 452 MiB, heapUsed 249 MiB, 240% CPU по времени одного ядра, задержку event loop p95 117 мс / max 287 мс; DB 21 соединение / 4 активных / 0 ожидающих блокировку в момент выборки. В 20:29:13.801 UTC outbox содержал 102 события, возраст старшего 6,39 с. Сэмплирование каждые 5 секунд не исключает короткую очередь пула или блокировки между снимками. CPU может превышать 100% за счёт потоков и нативных операций.

Версии различаются и зафиксированы отдельно: прежний локальный 500 использовал Node 24.8.0; свежие standalone-регрессии — bundled Node 24.19.0 и k6 1.6.1 (`2ac2bb560e`, Windows/amd64, Go 1.25.7); проверяемый Railway runtime — Node 22.23.3. Воспроизведение одной категории отказа на другом minor Node не является сравнением производительности этих runtimes.

Дополнительный разбор по маршрутам показывает p95 успешных операций такси: accept 1775 мс, arrive 1933 мс, start 1930 мс, complete 1740 мс. Объединённый p95 process 1160 мс смешивает операции такси и еды и скрывает часть этого хвоста. Успешные ответы главным образом задерживались в `http_req_waiting`, а не в connect/send/receive: например process waiting p95 1159,7 мс, соединение p95 0. Это ещё не разделяет выполнение приложения, очередь Prisma и планирование процессов общего хоста.

HTTP-авторизация и WebSocket-подключение проверяют живую сессию через БД. Каждое `session:ready` инициирует канонические HTTP-запросы; при 475 переподключениях возникает дополнительная волна чтений и проверок доступа. Такая волна — проверяемая гипотеза позднего хвоста, а не доказанная причина. Для различения нужны измерения очереди пула/SQL/обработчиков и независимый генератор. Кэшировать разрешения или обходить проверки сессии для улучшения цифр запрещено.

Все 200 уникальных заказов завершены, 100 комиссий и истории с правильными акторами подтверждены отдельной проверкой. Прогон всё равно **FAIL**: read p95 648 мс превышает действующий критерий 500 мс; 278 неожиданных ответов API; 3 неуспешных первоначальных канонических синхронизации; 5 connect_error. Детали этих пяти ошибок прежний Socket.IO-инструмент не сохранял. Нулевой счётчик распознанных timeout не доказывает отсутствие всех возможных категорий таймаутов. Отсутствие обрывов и последующее успешное переподключение не отменяют ошибку первоначальной синхронизации. 1000 и peak2x не запускались.

## Изолированная проверка генератора и исправление

Без приложения, БД, Socket.IO и реальных аккаунтов выполнен тест 480 VU против отдельного Node HTTP-реестра в памяти. При штатном backlog получены 1327 отказов кода 1212 / `dial: connection refused`, затем все 480 корректных слотов. Контроли backlog=1 и backlog=2048 также воспроизвели отказы; в контроле 2048 — 1204. Следовательно, этот дефект транспорта/регистрации воспроизводится без бизнес-кода, но данные не определяют точную причину в Windows/k6/очереди подключения и не объясняют позднюю задержку API. Увеличивать backlog по этим данным недостаточно. `ECONNRESET` на серверной стороне при завершении клиентов сохранён отдельно и не подменяет клиентскую категорию 1212.

Исправление ограничено генератором. Четыре процесса k6 имеют отдельные роли clients/drivers/restaurants/booking; в каждом закрытом сценарии slot=VU-1 проверяется по неизменной квоте. Чужая роль, лишний VU, дубликат идентичности, несовпадение SHA fixture или кандидата блокируют запуск. Один booking-процесс сохраняет уникальную scenario.iterationInTest и исходный бюджет до первого HTTP. Все четыре процесса проходят отдельный ограниченный readiness-барьер; только затем начинается общий измеряемый профиль. Профиль 120 секунд, 80/15/5, интервалы, 60 секунд бронирования/60 секунд дренажа, timeouts, переподключение и критерии остаются прежними. REST-порт управления каждого k6 выделяется как отдельный `127.0.0.1:0`, чтобы процессы не конфликтовали на стандартном 6565.

Уточнение оптимизации каталога `cc4ab2f`: SingleFlight хранит только незавершённый promise и освобождает ключ при успехе/ошибке. Пересекающиеся GET разделяют один снимок выполняющегося DB-чтения; запись, завершившаяся во время этого чтения, проверяется следующей волной. Завершённый JSON не переиспользуется, TTL нет. Это не обещание линейной свежести для каждого одновременного GET. Оформление отдельно перечитывает каталог и проверяет актуальные цены, модификаторы и доступность под транзакционной блокировкой; capability заголовок не меняет этот контроль.

Все исходные потоки сохраняются; startup-HTTP и его ошибки показываются отдельно, их не выдают за действия пользователей. p95 вычисляется из объединённых сырых значений, не усредняется по четырём p95. Параметры и полная длительность каждой роли, совпадение количества сырых HTTP-запросов с отчётом, каждый актор, созданный/принятый/завершённый заказ и комиссия обязательны. HTTP-ошибки и причины connect_error/fetch/disconnect теперь сохраняются ограниченно без токенов; счётчики учитывают также ошибки за пределами диагностического лимита.

Артефакты: `.local/load/500-20261012T202801494Z-offline-diagnosis.json`, `registry-isolation-coded-summary.json`, все исходные raw/log/report; регрессии `scripts/test/load-role-metrics.test.mjs` и `load-scenario.test.mjs`. Фактический API/БД-замер с исправленным генератором пока не выполнен. Синтетическое протокольное испытание генератора не заменяет его.

Проверки исправления, действительно выполненные: полный набор operations 31/31 до последнего выделения error-diagnostics; последние 6/6 focused после него; синтаксис изменённых Node-модулей. Реальный 120-секундный k6 + настоящий Socket.IO против собственного протокольного сервера **без БД/приложения** подтвердил 38/8/2 акторов, 20 уникальных booking actors, 20 завершённых моделируемых заказов, 1312 HTTP профиля + 7 startup, p95 read 32 мс, 48 ready / 48 reconnect / 96 canonical, все прежние aggregate gates. В этом первом протокольном прогоне также обнаружены нефатальные конфликты стандартного контрольного порта k6; исправление `--address 127.0.0.1:0` проверено отдельно четырьмя одновременными короткими k6-процессами — все code=0, ошибок control API нет. Это разделение проверок сохранено: полный 120-секундный прогон после изменения **только аргумента контрольного порта** не повторялся. Сырые результаты — `.local/load/role-process-probe-latest.json`, отдельная директория первого прогона и `k6-control-port-regression.json`. Полная mandatory-проверка нового кандидата и измерение API/БД остаются задачей последующего этапа.

## Повторное испытание с изолированным генератором

Перед запуском root должен связать **точный** новый sourceDigest, runtime/build digest, миграции, UTC, конфигурацию и синтетическую namespace с выбранным DEV-target. Использовать отдельную временную БД/процесс, не действующие 33 таблицы DEV-сервиса. Проверить, что cleanup удаляет только этот namespace/объект и никакой реальный или тестовый магазин/код входа. Требуемые облачные/платные ресурсы, DNS и резервирование не создаются и не меняются автоматически.

Для убедительного результата генератор должен работать на другом хосте/контейнере с отдельно записанными CPU/RAM, FD/TCP, RTT и clock offset, не в cgroup тестируемого API. Если бесплатного отдельного генератора пока нет, локальный либо co-located запуск можно использовать для диагностики с этой явной оговоркой, но не объявлять его пропускную способность пределом Railway. В текущем Railway API и PostgreSQL имеют отдельные cgroup-пределы 8 CPU/8 GB; проверяемый runtime Node 22.23.3, PostgreSQL 18, max_connections=500. Это отличается от прежнего локального профиля; параметры фиксируются заранее, не подменяются во время лестницы. Prisma pool для кандидата также должен быть записан фактически.

Лестница остаётся 50 → 100 → 250 → 500 → 1000, каждый уровень 120 секунд с прежним бюджетом бронирования и дренажом. Переход только после полного успеха предыдущего. Peak2x проводится только после normal1000 и меняет исключительно заранее записанные интервалы foreground/GPS, сохраняя бюджет/права/полное завершение. Отдельно учитывать setup и первоначальный cold ramp, 60-секундное переподключение и последовательность более поздних повторов с тем же профилем. Не вырезать первые/пиковые секунды из полного SLO; отдельные интервалы нужны для диагноза, а не для обхода провала.

Обязательны прежние агрегатные критерии: read p95<500 ms, неожиданные 429=0, распознанные request_timeouts=0, unexpected_responses<1% (координатор сохраняет прежний более строгий запрет неожиданных ответов), dropped_iterations=0, create/accept/process>99%, idempotent retry=100%, полный booking budget и уникальные DB/endstate/history/commission. Socket.IO: каждый актор ready, запланированное переподключение и обе канонические синхронизации успешны, pending=0, неожиданные disconnect/connect_error/expired/unavailable/429=0. Сохранить результаты всех провалов и остальные типы transport/timeout, чтобы узкий timeout-counter не скрывал нераспознанные ошибки.

На каждом уровне сообщать отдельно: RPS/число запросов, p95 чтения/quote/create/retry/accept/arrive/start/complete/food actions/GPS, 5xx/429/all transport/timeouts/drop, уникальные заказы/истории/комиссии, WS ready/reconnect/resync, outbox lag/pending, RSS/CPU/event loop/GC, pool wait/SQL p95/active/locks/connections, генератор CPU/RAM/FD/TCP и HTTP connect/wait/receive. Сравнивать поздний хвост с reconnect burst и очередью БД, не с общим спокойным средним.

Заключение сейчас: прежний локальный 500 остаётся неуспешным; причина startup регистрации воспроизведена независимо от приложения, но точная системная причина и поздний хвост не установлены. Новое испытание Railway и оптимизация расходов требуют результата того же нового кандидата. Производственная готовность этим документом не подтверждается.

### Независимый read-only диагноз outbox phase3

**Подтверждено в проверенном исходнике:** `OrderOutboxWorker.tick` вызывается через `@Interval(1000)`, защищён `running`, за вызов делает один `flush(limit=25)`. Flush claims25 rows с `SKIP LOCKED` в транзакции, ставит lease30s/attempts+1, затем последовательно ждёт dispatch и отметку delivered каждой строки. При одном worker это верхняя граница25 claimed events/s даже при нулевой стоимости I/O; медленный flush может дополнительно пропускать ticks. Это не ограничение Railway или PostgreSQL.

**Подтверждено измерением:** уbaseline1000 максимальный age20,293284s в23:15:21.911 и уpeak24,833095s в23:17:31.997 совпали с maxAttempts0/backoffPending0. В этих snapshots **все pending ещё не были claimed ни разу**: старейшая задержка была очередью до первой попытки, а не failure/retry/30s lease. Peak drain:23:17:26.992→31.997→36.998→42.001 pending369→245→120→0, то есть примерно24,8/25,0/24,0 события/s. Pending619 в23:17:06.976 также весь attempts0. Некоторые другие snapshots с attempts1/availableAt>now соответствуют первой in-flight lease; sampler название `backoffPending` не различает lease и retry.

**Объяснение, поддержанное исходником и наблюдением:** DB triggers создают отдельные durable rows для order/food insert и изменений status, а также taxi offer insert/change. Для стандартного taxi полного lifecycle с одним offer — минимум6 rows, для food —5. При400 заказах это минимум2200 events за профиль, причём мутации сосредоточены в первых booking/processing волнах, а не распределены равномерно120s. Наблюдаемая drain скорость почти достигает программной границы25/s и очередь возникает до claim. Cadence/batch cap поэтому подтверждённый вклад в задержку, заслуживающий первого ограниченного исправления; точное распределение времени между cap и DB/serialization/auth ещё не измерено.

**Дополнительные затраты по исходнику, без подтверждённых длительностей:** taxi delivery проверяет существование order, повторно собирает snapshot через несколько ORM reads/ratings/history, читает offer recipients, а gateway проверяет JWT+актуальную refreshSession/user membership по каждому distinct token для каждого dispatch. Food dispatch также ждёт recipient authorization. Эти операции последовательны; operation-local lookup разделяет только одинаковый token в одном событии, завершённые результаты не кешируются между событиями. Background audit дополнительно проверяет sockets каждые10s. Существующие order события адресованы user rooms; нельзя утверждать, что каждое order событие делает950 authorization checks. Число фактических SQL и их latency/pool waits не трассировались.

**Не подтверждено:** outbox SQL failure/auth failure/retries как причина хвоста, постоянная нехватка CPU/RAM, платформа Railway как причина, универсальный event-delay SLA. `deliveredAt` означает завершённую попытку отправки server-side; пользовательский ack/delivery-age для каждого события не измерялся. Client canonical resync и HTTP polling дают восстановление состояния, но не доказательство своевременности каждого push. Backend агент отдельно готовит ограниченный fix; агент анализа не изменял worker/authorization/schema/thresholds и не повторял API/DB испытания.

Immediate publish и outbox могут отправлять один и тот же canonical snapshot повторно; lifecycle/commission idempotence подтверждена отдельными predicates. Рост durable queue сам по себе не доказывает, что primary event не пришёл, но показывает ограниченную пропускную способность резервного восстановления. Снижение возраста этой очереди должно измеряться отдельно, сохраняя direct publish, fresh authorization и защиту от stale lease.

Независимая offline повторная проверка неизменённых `assertHttpThresholds`/`assertLoadResults`/`socketAcceptance` над saved snapshots прошла6/6: полные status histories/declared actors/unique commissions, ready+canonical каждого account, four-role startup/child exits и candidate tuple. Orders IDs1160 и commission keys580 различны между ступенями. Артефакт `phase3/acceptance-recheck.json` подтверждает пересчёт этих predicates, сохраняя отдельным риск20–25s delivery queue.
