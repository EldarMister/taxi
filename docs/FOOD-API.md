# Доставка еды

Модуль работает рядом с такси и использует существующие SMS-сессии. Все суммы — целые сомы (`KGS`). Заказы хранятся в PostgreSQL независимо от заказов такси.

Каталог, история заказов, баннеры и административные маршруты включены в текущую серверную сборку и развёрнуты на публичном API Railway. Прежний ответ `Cannot GET /api/food/orders/history` относился к развёртыванию без модуля доставки. Управление оператором и сведения о публикации описаны в [ADMIN.md](ADMIN.md).

## Каталог

`GET /api/food/catalog` возвращает `{ restaurants, paymentMethods, isDemo }`.

Форма ресторана описана в `server/src/food-catalog.ts`: название, оценка и число отзывов, кухня и категории, интервал доставки `etaMin`/`etaMax`, `deliveryFee`, `minimumOrder`, адрес, телефон или `null`, ключи локальных изображений, необязательные `imageUrl` и `heroImageUrl`, `menuCategories`, `dishes`, `options`, `isDemo`.

`dishes` содержат `id`, `name`, `category`, `description`, `portion`, `weightGrams`, `price`, `imageKey`, необязательные `heroImageKey`, `imageUrl`, `heroImageUrl`, `available`, разрешённые `optionIds`. Дополнения содержат `id`, `name`, `price`, `imageKey` и необязательный `imageUrl`. Стоимость дополнения начисляется за каждую порцию. URL загруженного изображения имеет вид `/api/content/media/:id` и разрешается относительно корня API-сервера; также поддерживаются HTTPS-ссылки.

В `paymentMethods` доступны `CASH` («Наличными»), `CARD` («Картой при получении»), `ONLINE` («Онлайн-оплата»). Только `CASH.available` равен `true`; два других способа пока отклоняются сервером. Эквайринг и терминалы ресторанов не подключены.

## Оформление

`POST /api/food/orders` требует Bearer-токен клиента:

```json
{
  "requestId": "food-request-0001",
  "restaurantId": "sushi-roll",
  "items": [{ "dishId": "philadelphia", "quantity": 2, "optionIds": ["soy"] }],
  "fulfillment": "DELIVERY",
  "address": "ул. Киевская, 123, кв. 12",
  "comment": "Не звонить в дверь",
  "paymentMethod": "CASH"
}
```

`requestId` — 8–100 символов; сохраните его до определённого результата отправки и повторяйте тот же запрос при сетевом сбое. Одинаковые повторы возвращают прежний заказ даже после его завершения. Изменение данных с тем же ключом даёт `409`. Новый ключ во время активного заказа еды также даёт `409`. Заказ такси этому не мешает.

В корзине 1–50 строк и не более 99 порций суммарно; количество — целое число 1–99. Дополнения должны принадлежать блюду, не повторяться; нельзя заказать недоступное блюдо или блюдо другого ресторана. Сервер вычисляет `subtotal`, `deliveryFee`, `total` по сохранённому каталогу. Присланные клиентом суммы, цены и лишние поля отклоняются. Адрес доставки — 5–300 символов после удаления крайних пробелов. Для `PICKUP` адрес сохраняется пустым, доставка бесплатна. Комментарий — до 500 символов.

Возвращается `FoodOrder`: `id`, `status`, `createdAt`, `updatedAt`, `completedAt` (ISO-даты или `null`), `restaurant` (снимок `id`, `name`, `rating`, `reviewCount`, `address`, `phone`, `imageKey`, `etaMin`, `etaMax`), `items`, `subtotal`, `deliveryFee`, `total`, `currency`, `fulfillment`, `address`, `comment`, `paymentMethod`, `isDemo`. Строка заказа: `dishId`, `name`, `portion`, `imageKey`, `quantity`, `unitPrice` (цена блюда без дополнений), `options`, `lineTotal` (с дополнениями и количеством). Каталог после оформления не изменяет сохранённый заказ.

Снимки ресторана, блюда и дополнений сохраняют `imageUrl`, если он задан. Изменение цены, названия или фотографии в меню не меняет прежний заказ. Во время оформления сервер блокирует запись ресторана и повторно проверяет роль клиента под блокировкой пользователя.

## Восстановление и статусы

- `GET /api/food/orders/active` — собственный активный заказ либо `null`.
- `GET /api/food/orders/history?period=all` — собственные последние 100 заказов; также `today`, `week` по времени Бишкека.
- `GET /api/food/orders/:id` — собственный заказ, чужой идентификатор возвращает `404`.
- `POST /api/food/orders/:id/cancel` — отмена своего заказа только на этапах `PLACED`, `CONFIRMED`; повтор отмены безопасен.
- `PATCH /api/admin/food/orders/:id/status` — только `ADMIN`; тело `{ "status": "CONFIRMED", "reason": "..." }`, причина необязательна.

Доставка: `PLACED → CONFIRMED → PREPARING → READY → DELIVERING → COMPLETED`. Самовывоз: `PLACED → CONFIRMED → PREPARING → READY → COMPLETED`. Администратор может отменить любой незавершённый заказ. Пропуски этапов и возврат из завершения запрещены. История каждого перехода хранит исполнителя, причину и дату. Статусы меняет оператор в панели управления; автоматического таймера подтверждения, приготовления или движения курьера нет. Отдельные кабинеты ресторанов и автоматическое назначение курьеров не подключены.

После фактического создания, отмены или изменения статуса клиент получает `food:order:updated` с заказом, администраторы — `admin:changed`. Идемпотентные повторы и запросы уже установленного статуса не публикуют повторное изменение. Клиент также восстанавливает данные после возврата в приложение и использует резервный опрос.

## Управление каталогом и баннерами

Все маршруты `/api/admin/*` требуют административную сессию с входом по паролю.

| Маршрут | Назначение |
|---|---|
| `GET /api/admin/restaurants` | `{items,total}`; записи с `id`, `catalog`, `active`, `isDemo`, `sortOrder`, `updatedAt` |
| `POST /api/admin/restaurants` | Создание: `{id?,catalog,active?,isDemo?,sortOrder?}` |
| `PATCH /api/admin/restaurants/:id` | Обновление полного `catalog` и/или настроек; идентификатор не меняется |
| `DELETE /api/admin/restaurants/:id` | Архивация: `active=false`, история заказов и меню сохраняются |
| `GET /api/content/banners` | Публичные `{banners}`: не больше трёх активных, по `sortOrder` |
| `GET /api/admin/banners` | Все баннеры, включая черновики: `{items,total}` |
| `POST /api/admin/banners` / `PATCH /api/admin/banners/:id` | Создание и редактирование баннера |
| `DELETE /api/admin/banners/:id` | Удаление баннера |
| `POST /api/admin/media` | Multipart-поле `image`; ответ `{url}` |
| `GET /api/content/media/:id` | Публичное нормализованное изображение из PostgreSQL |

Каталог проверяется целиком: уникальные идентификаторы, существующие категории и дополнения, целые неотрицательные цены, допустимые URL и размеры списков. Изменения меню, фотографий, доступности и порядка сохраняются в базе. Созданный ресторан по умолчанию скрыт и не является демонстрационным.

Баннер содержит `title`, `subtitle`, `imageUrl`/`imageKey`, `actionType` (`NONE`, `FOOD`, `TAXI`, `RESTAURANT`), `restaurantId`, `sortOrder`, `active`. Для действия `RESTAURANT` нужен существующий ресторан. Четвёртая одновременная активация возвращает `409`; транзакционная блокировка защищает лимит и при параллельных запросах. Черновиков может быть больше трёх.

Загрузка принимает JPEG, PNG и WebP до 8 МБ и 24 мегапикселей, сверяет MIME с байтами и преобразует изображение в WebP до 2000 пикселей по длинной стороне. SVG, повреждённые и многокадровые файлы отклоняются. Метаданные удаляются, изображения хранятся в PostgreSQL. Редактирование каталога и баннеров отправляет `content:changed` подключённым приложениям и `admin:changed` администраторам; административные изменения фиксируются в журнале в той же транзакции.

## Демо и запуск

Миграция `202609080001_food_delivery` создаёт каталог, заказы и историю, ограничения сумм и один активный заказ еды на клиента. `npm --prefix server run db:migrate` применяет миграции к настроенной базе. `NODE_ENV=development` и `npm --prefix server run db:seed` явно добавляют четыре демо-ресторана из референсов; существующие записи не перезаписываются. Телефоны демо-ресторанов не заданы. Город Кочкор-Ата и адрес Sushi Roll «ул. Ленина 12» перенесены из референсов; записи помечены `isDemo=true`.

Все демо-записи имеют `isDemo=true`; вне `NODE_ENV=development` они исключены из каталога и новые заказы из них запрещены. Демо-заказ не отправляется настоящему ресторану. Для рабочего каталога оператор добавляет согласованные с рестораном данные через панель и устанавливает `isDemo=false`, `active=true`. Публичное обновление API развёрнуто; в каталог добавлены четыре демонстрационных ресторана. SMS остаётся development, отдельное подключение ресторанов и курьеров не выполнено.

## Проверки

`npm --prefix server test` включает расчёт цен, ограничения корзины, проверку каталога и изображений, обязательный адрес, недоступные оплаты, привязку ключа повтора к содержимому и права смены статуса. `npm run test:local` применяет миграции и запускает HTTP-проверки только на отдельной локальной `taxi_test`: параллельные повторы заказа, доступ к своим данным, серверная цена, история после редактирования меню, административные переходы, самовывоз, отмена, Socket.IO, загрузка фото и конкурентная активация баннеров. Сценарии существующего такси также проверяются.

После добавления панели локально прошли миграции, TypeScript/Prisma build и 50 серверных тестов: 27 модульных и 23 интеграционных на настоящем PostgreSQL. Публичное развёртывание Railway имеет статус `SUCCESS`; снаружи подтверждены CORS для панели и доставка `admin:changed` при изменении баннера. Реальные рестораны, курьеры и эквайринг в проверке не участвовали. Подробности публикации и резервной копии — в [ADMIN.md](ADMIN.md).
