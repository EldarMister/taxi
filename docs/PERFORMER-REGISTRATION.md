# Регистрация исполнителей

Новый модуль работает поверх существующей телефонной авторизации. Клиентское приложение авторизации не менялось: в сборке `Atlas pro` пользователь с ролью `CLIENT` после входа попадает в анкету исполнителя.

## Поток

`buildRegistrationSteps()` формирует шаги из выбранных направлений и способов доставки. Общие личные данные, удостоверение личности и водительские права не дублируются. Такси, грузовой транспорт и отдельный моторный транспорт курьера хранятся раздельно; транспорт такси или грузовой роли можно явно переиспользовать для курьера.

Статусы анкеты:

```text
NOT_STARTED → DRAFT → SUBMITTED → UNDER_REVIEW
                                      ├─ CORRECTION_REQUIRED
                                      ├─ APPROVED
                                      ├─ REJECTED
                                      └─ BLOCKED
```

Роли и файлы имеют собственные статусы проверки. Экран регистрации рассчитывает прогресс динамически и восстанавливает сохранённый `currentStep`.

Одобренное направление может стать рабочим, пока другие ещё проверяются. В `roleStatuses` сервер явно возвращает `operational`, а на уровне анкеты — `canActivate` и `activatedAt`. Общий статус при этом остаётся `UNDER_REVIEW`, `CORRECTION_REQUIRED`, `REJECTED` или `BLOCKED`, пока не завершены все выбранные направления.

## Сохранение и файлы

- Изменение сначала записывается в зашифрованное хранилище устройства, затем отправляется на сервер с `version`.
- Синхронизация сериализована; конфликт версии автоматически перебазирует локальный черновик на актуальную серверную версию.
- Офлайн-файлы остаются в очереди и отправляются после восстановления сети.
- Камера запрашивается только после собственного информационного экрана. Документы можно снять камерой с рамкой, выбрать из галереи или как файл, затем проверить в предпросмотре.
- Сервер сверяет MIME с сигнатурой, ограничивает размер и разрешение, не возвращает байты в обычном ответе и отдаёт файл только владельцу либо проверяющему через защищённый маршрут.
- Полные платёжные реквизиты и токены провайдера не принимаются. В черновике хранятся только тип платёжного способа и последние четыре цифры.
- Удостоверение, права и страховки нельзя одобрить без `expiresAt`. Даты удостоверения и прав выводятся из анкеты; срок страховки может передать клиент или указать оператор при одобрении.
- Фоновая проверка переводит документ в `EXPIRING` за 30 дней и в `EXPIRED` в дату окончания. Просрочка сразу снимает связанные dispatch-capabilities, возвращает роль на исправление и разрешает замену файла. Полная legacy-проекция откладывается до завершения активного заказа, но новые заказы уже не выдаются.
- Основной транспорт каждого направления остаётся в `taxiVehicle`, `cargoVehicle` или `courierVehicle`. До пяти дополнительных машин передаются только в `vehicles[]`: уникальный `clientId` формата `v-[a-z0-9]+`, `usage` (`TAXI`, `CARGO`, `COURIER`) выбранного направления и, для грузовой машины, собственный `equipment`.
- Документы дополнительной машины используют стабильные слоты `vehicle_<clientId>_registration`, `vehicle_<clientId>_insurance`, при аренде `vehicle_<clientId>_rental` и фотографии `vehicle_<clientId>_photo_<side>`. Страховка всегда требует срок действия. Поля исправления возвращаются в каноническом виде `vehicles.<clientId>.<field>` и не открывают другие машины или поля.
- При переиспользовании транспорта курьером пустой `courier.existingVehicleClientId` означает основной транспорт выбранного `existingVehicleUsage`; непустой идентификатор обязан точно ссылаться на дополнительную машину того же usage. Legacy-проекция по-прежнему хранит один автомобиль и честно сообщает конфликт через `projectionIssueCode`.

## API исполнителя

```text
GET    /driver/registration
GET    /driver/registration/config
PATCH  /driver/registration
POST   /driver/registration/uploads/:slotKey
GET    /driver/registration/uploads/:slotKey
DELETE /driver/registration/uploads/:slotKey
POST   /driver/registration/submit
POST   /driver/registration/resubmit
POST   /driver/registration/activate
```

Первый `PATCH` или upload идемпотентно создаёт одну анкету благодаря уникальному `userId`. Повторный submit уже отправленной анкеты возвращает текущее состояние и не создаёт копий.

`submit` и `resubmit` принимают `truthConfirmed`, `termsAccepted`, `acceptedConsentIds` и актуальный `legalTermsVersion`; обязательные согласия и допустимые идентификаторы берутся только из серверного конфига. `activate` доступен после появления хотя бы одного `APPROVED` + `operational` направления и возвращает `{ application, user }`.

Административная проверка доступна через `GET /admin/performer-applications`, detail и отдельные операции start-review, role/upload decision и защищённый file preview. Решения требуют `expectedVersion`, причины отказов/исправлений, записываются в аудит без документов и платёжных данных.

Жизненный цикл ставит в общую push-очередь события `registration:submitted`, `registration:review_started`, `registration:document_approved`, `registration:document_expiring`, `registration:document_expired`, `registration:correction_required`, `registration:approved`, `registration:rejected`, `registration:blocked` и `registration:activated`. У таких заданий `orderId = null`, а allow-listed payload содержит только безопасные routing-метаданные (`applicationId`, роль, слот, статусы и `reasonCode`) — без `reasonText`, документов и персональных данных.

## Миграция

Перед запуском сервера применить Prisma-миграции:

```text
cd server
npm run db:migrate
```

Старый `DriverProfile` оставлен для совместимости действующих водителей и диспетчеризации. Одобрение роли подготавливает совместимый legacy-профиль, но роль пользователя не повышает. Роль `DRIVER` выдаётся только по явному `POST /driver/registration/activate`; остальные направления могут продолжать проверку. Устаревший `POST /driver/register` закрыт с ответом `410 Gone`, поэтому выпуск требует обновления старых клиентов.

Legacy-диспетчеризация хранит один основной автомобиль. Если одобрены направления с разными автомобилями, только совместимый с основным профилем допуск получает `operational: true`; у остальных возвращается явный `projectionIssueCode`. Пеший/вело-курьер может активировать профиль и выйти на линию без фиктивного автомобиля, но назначение пеших/вело-заказов требует отдельного типа заказа и диспетчера, которых в текущем legacy-модуле ещё нет.
